# arm64 image availability for the release pins and Docker Desktop identity facts on Apple Silicon

Research ticket [#162](https://github.com/hazeion/fleur/issues/162), map [#160](https://github.com/hazeion/fleur/issues/160). Date: 2026-11-09. Registry observations below were made on that date from an Intel macOS host with the Docker CLI 29.9.2 and the anonymous Docker Hub registry API; no image was pulled and no daemon was running.

## Question

Fleur's release pins include exact Bun image digests and a PostgreSQL image digest, and the readiness smoke uses an architecture-specific Bun image. For the pinned versions, do `linux/arm64` images exist, are the pinned digests manifest-list (index) digests covering both architectures or per-architecture digests, and how should a release record them? Separately, which identity facts does Docker Desktop on Apple Silicon report that the readiness profile compares (kernel flavour, cgroup driver and version, security options, operating mode, virtualization settings), and how do Rosetta-emulated amd64 containers appear in `docker info` and in a container?

## Summary answer

1. The two `oven/bun` pins are **per-platform OCI image manifests**, not an index: `c017a211…` is `linux/amd64` and `bf9d5b1f…` is `linux/arm64`. Both are the two platform entries of the `oven/bun:1.4.3` index `sha256:ec06c3b6…`, both carry `org.opencontainers.image.version=1.4.3` and the same source revision, and both are Debian trixie based. The arm64 image for the exact pinned Bun release therefore exists and is already the pin Fleur uses on arm64 hosts. The two `ubuntu` controller bases in `src/runtime/native/build.ts` are likewise per-platform manifests of `ubuntu:24.04` (amd64 and arm64/v8).
2. The `postgres` pin `74935e72…` is an **OCI image index** with eight platform manifests (amd64, arm/v5, arm/v7, arm64/v8, 386, ppc64le, riscv64, s390x) plus eight `unknown/unknown` attestation manifests. Its `linux/arm64/v8` member is `sha256:a63b24165ea0eacced7585766d790ac08bbaefe10a1841f87783a4505d29a69c`; its amd64 member is `sha256:885953109528ad3dfc90362b1a6f50a78620b5315be19f187753d267e484dc5b`. Both configs report `PG_VERSION=18.6-1.pgdg13+2`. The daemon selects the arm64 member automatically on an arm64 host.
3. A release should record, per image, the index digest it was resolved from and, per architecture, the platform manifest digest; where a local image ID is compared it must also allow for the image store: the classic store identifies an image by its config digest, the containerd store (Docker Desktop default, Engine 29 default on fresh installs) by the registry digest it was pulled by. Fleur's production artifact manifest already records both identities for saved images. Tags move (every tag checked had already moved away from the pinned digests), so pins stay reachable only by digest.
4. Docker Desktop on Apple Silicon reports `Architecture: aarch64`, `Kernel Version: <X.Y.Z>-linuxkit`, `Operating System: Docker Desktop`, `OSType: linux`, `Cgroup Driver: cgroupfs`, `Cgroup Version: 2`, and `Security Options: seccomp (Profile: builtin), cgroupns` in published dumps; the kernel flavour `-linuxkit`, the cgroup facts and the security options are the same strings as Fleur's measured Intel Desktop row, so only the architecture facts change. `docker info` carries no field for the VMM choice or for Rosetta. Some Desktop dumps report `seccomp Profile: unconfined`, which Fleur's parser would refuse as an unknown security option; the cause was not located in a primary source.
5. Rosetta appears to Fleur in two unrelated ways. If the Fleur CLI itself is an x64 Bun running under Rosetta, `sysctl.proc_translated` is 1 and the `translated` identity fact mismatches. An amd64 container on an arm64 daemon is visible only through the image: `docker image inspect` reports the image config's `Architecture: amd64` while `docker info` still reports `aarch64`; the smoke's architecture check and the `image` identity fact both refuse it. Inside the VM, Docker Desktop registers Apple's `rosetta` binary through `binfmt_misc` for x86_64 ELF files, so emulation is transparent to the container's processes. Docker VMM does not support Rosetta (amd64 emulation is slow there); Rosetta needs the Apple Virtualization framework VMM.

## Findings

### 1. What Fleur pins today

- `src/setup/profiles.ts` maps `x64` to `oven/bun@sha256:c017a211c49a21adc0e49dda7b60ac8112887c3d9465e01427f434ed107c830e` and `arm64` to `oven/bun@sha256:bf9d5b1f01be2de7cec5aa6e3977e8848f7ab9a307c6c3a8af7a50a27e609023`. `src/setup/readiness.ts` requires a measured row's `image` to equal `smokeImages[host.architecture]`, and the row's `image` is one of the exact identity facts (`identityFacts` = system, distribution, architecture, translated, daemon, server, product, cgroupDriver, cgroupVersion, operatingMode, securityOptions, image, kernel).
- `src/runtime/native/build.ts` chooses the same two Bun digests as the worker base and `ubuntu@sha256:a2d43bff…` (amd64) or `ubuntu@sha256:18b33ff3…` (arm64) as the controller base, keyed on `docker info --format {{.Architecture}}` (`aarch64`/`arm64` versus `x86_64`/`amd64`).
- `src/runtime/development/postgres.ts` pins `postgres@sha256:74935e72241653ca55e0414067e6d8763aceb8a810eb51b452253ec3dcfc4336`, described in source as a "digest-pinned multi-architecture PostgreSQL image"; `tests/runtime/owned-postgres.ts` pulls the same digest when absent.
- `src/setup/smoke.ts` accepts an image only when `Id` is a `sha256:` digest, `RepoDigests` contains the pinned reference (or, for a loaded artifact, `Id` equals it), `Os` is `linux` and `Architecture` equals `amd64` for an x64 host or the host architecture string otherwise.
- `src/setup/host.ts` derives the darwin `translated` fact from `sysctl.proc_translated`, only trusted when `hw.cputype` agrees with `process.arch`; readiness treats any value other than `false` as an identity mismatch.
- `experiments/compatibility/isolation/README.md` recorded, at inventory time, the `oven/bun:1.4.3` index `sha256:ec06c3b6cea04192ae6770c434f668ca41d343ad19fa6472216c7b48be39c598` with the amd64 and arm64 member digests above; `experiments/compatibility/evidence.md` records the arm64 native probe executed on an Ubuntu 24.04 arm64 GitHub runner against the arm64 member, and the PostgreSQL index resolving on amd64 (classic store) to image ID `sha256:29754c7520f4b9654cf8ff98e19ac73b88e255c3a53f6236ebe9d52249bb6df3`.

Both Bun configs (fetched as blobs from `registry-1.docker.io/v2/oven/bun/blobs/<digest>`) carry identical OCI labels: `org.opencontainers.image.version=1.4.3`, `org.opencontainers.image.revision=c6da4a4d3010e5553438c60f6bd76d981976867c`, `org.opencontainers.image.source=https://github.com/oven-sh/bun`, `org.opencontainers.image.created=2026-10-10T05:28:31.623Z`. Their history begins with `# debian.sh --arch 'amd64' out/ 'trixie' '@1791158400'` and `# debian.sh --arch 'arm64' out/ 'trixie' '@1791158400'` respectively, that is the same Debian trixie base snapshot.

Anonymous registry resolution of the tag `oven/bun:1.4.3` on 2026-11-09 still returns index `sha256:ec06c3b6…` with exactly these two platform members plus two `attestation-manifest` entries (`unknown/unknown`), matching the isolation README. The tag `oven/bun:1.4.3-debian` is a different index (`sha256:923bedb3…`) with different member digests, so the default `1.4.3` tag is what the pins came from.

The pins are therefore **per-platform manifest digests**, which is what makes `oven/bun@<digest>` unambiguous on any host: pulling such a reference involves no platform negotiation. Per the [OCI image index specification](https://github.com/opencontainers/image-spec/blob/main/image-index.md), an index "is a higher-level manifest which points to specific image manifests, ideal for one or more platforms", each `manifests` entry carrying `platform.architecture`/`platform.os` using Go `GOARCH`/`GOOS` values and, for arm64, the variant `v8`; "if multiple manifests match a client or runtime's requirements, the first matching entry SHOULD be used". The `unknown/unknown` entries are BuildKit attestations: Docker's [attestation storage](https://docs.docker.com/build/metadata/attestations/attestation-storage/) sets `platform` to `unknown/unknown` "to prevent container runtimes from accidentally pulling or running the image described in the manifest" and annotates them `vnd.docker.reference.type: attestation-manifest`.

The Bun Dockerfile at the pinned revision ([`dockerhub/debian/Dockerfile` at `c6da4a4d`](https://github.com/oven-sh/bun/blob/c6da4a4d3010e5553438c60f6bd76d981976867c/dockerhub/debian/Dockerfile)) builds `FROM debian:trixie-slim AS build` / `FROM debian:trixie`, detects the architecture with `dpkg --print-architecture`, and downloads `bun-linux-x64-baseline.zip` for amd64 and `bun-linux-aarch64.zip` for arm64; any other architecture exits with `unsupported architecture`. The current [Bun installation docs](https://bun.sh/docs/installation) say "Bun provides a Docker image that supports both Linux x64 and arm64", that Bun "ships a single x64 binary per platform. It targets the Nehalem microarchitecture (SSE4.2) and selects AVX2/AVX-512 code paths at runtime when the CPU supports them", and that the `-baseline` assets "are kept as aliases of the single x64 binary for backward compatibility". Whether that alias statement already held for the 1.4.3 release asset was not verified here.

### 4. How a release should record per-architecture digests

Observed facts that constrain the record:

- The daemon's image store changes what a local image ID is. Docker Engine documents that "the containerd image store is the default storage backend for Docker Engine 29.0 and later on fresh installations" and that upgraded daemons keep overlay2 until switched ([Docker Engine containerd image store](https://docs.docker.com/engine/storage/containerd/)); Docker Desktop "uses containerd as its image store by default" ([Docker Desktop containerd image store](https://docs.docker.com/desktop/features/containerd/)) and "Fresh installations of Docker Desktop now use the containerd image store by default" since 4.34.0 ([Desktop release notes](https://docs.docker.com/desktop/release-notes/)). A moby maintainer explains the identity consequence: with the containerd image store "the OCI image index, manifests, and associated material … is preserved, so that (content-addressable) digests match the digests as known by the registry", and his `docker images --tree` example shows the top-level image ID equal to the index digest with only the host platform's layers present ([moby/moby#51779, thaJeztah](https://github.com/moby/moby/issues/51779)). The classic store's ID is the config digest ([pull reference](https://docs.docker.com/reference/cli/docker/image/pull/): "a SHA256 digest covering the image's configuration and layers"). Fleur's `src/runtime/production/artifact.ts` already encodes this: "A saved image has one identity per daemon store: its config digest on the classic store and its index entry digest on the containerd store."
- `RepoDigests` is the "List of content-addressable digests of locally available image manifests that the image is referenced from" and `Architecture` is the "Hardware CPU architecture that the image runs on" (image config), per the [moby API swagger](https://github.com/moby/moby/blob/master/api/swagger.yaml) `ImageInspect` definition. `docker image inspect --platform` (API 1.49+) can "Inspect a specific platform of the multi-platform image" ([image inspect reference](https://docs.docker.com/reference/cli/docker/image/inspect/)).
- `docker buildx imagetools inspect <ref>` prints the index `Digest:` and, under `Manifests:`, each `Name: <repo>@sha256:<member digest>` with its `Platform:` ([imagetools inspect reference](https://docs.docker.com/reference/cli/docker/buildx/imagetools/inspect/)); `docker manifest inspect` gives the same data without a daemon (used here). `--platform` on `run`/`pull` only applies "if server is multi-platform capable" and `DOCKER_DEFAULT_PLATFORM` is the "Default platform for commands that take the `--platform` flag" ([CLI reference](https://docs.docker.com/reference/cli/docker/)).

Recommendation derived from these facts (a research conclusion, not a decision):

1. For every pinned image, record the **index digest the pin was resolved from and the tag it was resolved from on the recorded date**, plus the **platform manifest digest per supported architecture** (`linux/amd64`, `linux/arm64`) and each member's **config digest**. The isolation README already has this shape for Bun; the PostgreSQL and Ubuntu records are incomplete (PostgreSQL has only the index and the amd64 config digest; Ubuntu has only the two manifest digests in code).
2. Keep using **platform manifest digests** wherever Fleur names an image for a specific architecture (smoke image, worker and controller bases): they need no platform negotiation and the same reference is valid under both image stores. Keep using the **index digest** where the daemon should choose the platform (the development PostgreSQL), but record the members so an arm64 host's resolved image can be checked against `a63b2416…`.
3. Where Fleur compares a local `Id`, accept the identity set `{config digest, pulled manifest digest or index digest}` rather than one value, as the artifact manifest already does; the readiness smoke's `RepoDigests.includes(<platform digest>)` check is store-independent and needs no change.
4. Treat the index's `unknown/unknown` attestation entries as non-platform members when enumerating.

Consequences for the catalog: the kernel grammar in `readiness.ts` parses `X.Y.Z-linuxkit` as identity `local:linuxkit` on both Intel and Apple Silicon, and the cgroup and security strings match the Intel Desktop row, so an Apple Silicon row would differ from the measured Intel row only in `host.architecture`, `info.Architecture`/`server.Arch`, the `image` (arm64 Bun digest) and whatever Desktop/Engine/kernel versions are measured. Because `host.architecture` is part of the target key, it is a new target (`darwin-arm64-desktop`) with its own floor, not an admission under the Intel floor.

Virtualization settings are **not** visible in `docker info`: none of the dumps nor the CLI example has a VMM or Rosetta field. The relevant Desktop facts come from settings and documentation:

- VMM choices on Mac are Docker VMM and the Apple Virtualization framework ([Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/): "Select **Docker VMM** for optimized container performance. Docker VMM is in Beta"); "Docker VMM replaced `libkrun` starting with Docker Desktop 4.86" and "HyperKit is deprecated" ([VMM page](https://docs.docker.com/desktop/features/vmm/)). "Current versions of Docker Desktop use the Apple Virtualization framework by default" ([Mac FAQs](https://docs.docker.com/desktop/troubleshoot-and-support/faqs/macfaqs/)); Desktop 4.44.0 release notes: "Apple Virtualization is now the default VMM for better performance and QEMU Virtualization is removed."
- Rosetta: the settings page lists "Use Rosetta for x86_64/amd64 emulation on Apple Silicon … Accelerate x86/AMD64 binary emulation on Apple Silicon … (Available with the Apple Virtualization framework VMM)" with Default "Disabled", while the [Settings Management reference](https://docs.docker.com/enterprise/security/hardened-desktop/settings-management/settings-reference/) gives `useVirtualizationFrameworkRosetta` Default `true`, and the 4.25.0 release notes say "Rosetta is now Generally Available for all users on macOS 13 or later" and "Rosetta is enabled by default on macOS 14.1 and later." The documentation is internally inconsistent on the default; the release note is the most specific statement. The JSON settings doc adds "Note: This also automatically enables `Use Virtualization framework`" ([configure JSON file](https://docs.docker.com/enterprise/security/hardened-desktop/settings-management/configure-json-file/)).
- "Docker VMM does not currently support Rosetta, so emulation of amd64 architectures is slow. Docker is exploring potential solutions." ([VMM page](https://docs.docker.com/desktop/features/vmm/)).
- Docker Desktop on Apple Silicon does not itself need Rosetta: "Rosetta 2 is no longer strictly required, however there are a few optional command line tools that still require Rosetta 2 when using Darwin/AMD64" ([Mac install](https://docs.docker.com/desktop/setup/install/mac-install/)).

### 6. How Rosetta-emulated amd64 containers appear

**Mechanism.** Apple's Virtualization framework exposes Rosetta to an arm64 Linux guest as a virtiofs share containing a `rosetta` binary; the guest registers it through `binfmt_misc` as the interpreter for x86_64 ELF files (`update-binfmts --install rosetta <mount>/rosetta --magic "\x7fELF\x02\x01\x01\x00…\x02\x00\x3e\x00" --mask "\xff\xff\xff\xff\xff\xfe\xfe\x00…" --credentials yes --preserve yes --fix-binary yes`), after which "the kernel uses the registered handler as the interpreter for that binary" ([Apple: Running Intel Binaries in Linux VMs](https://developer.apple.com/documentation/virtualization/running-intel-binaries-in-linux-vms)). Apple states the capability exists "in macOS 13 and later on Mac computers with Apple silicon", that "macOS 27 directly integrates support for Intel binary translation, without needing to install Rosetta", and that "Rosetta can run statically linked x86_64 binaries without additional configuration" while dynamically linked ones need their shared libraries in the guest. Docker Desktop uses exactly this path: a 4.67.0 release note fixes a "race condition between Rosetta `binfmt` registration and `virtiofs` device availability". On instruction sets, Apple says Rosetta "translates all `x86_64` instructions, including ones from the AVX and AVX2 instruction set, but it doesn't support the execution of AVX512 vector instructions" ([About the Rosetta translation environment](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment)); Bun's x64 binary "selects AVX2/AVX-512 code paths at runtime when the CPU supports them" ([Bun installation](https://bun.sh/docs/installation)).

**In `docker info`.** Nothing changes: the daemon runs natively in the arm64 VM and keeps reporting `Architecture: aarch64` and the `-linuxkit` kernel. There is no Rosetta or emulation field.

**In image and container metadata.** The emulated image is identified by its own config: `docker image inspect` returns `Architecture: amd64` ("Hardware CPU architecture that the image runs on", moby swagger) and `Os: linux`, and under the containerd store the per-platform manifest can be addressed with `--platform linux/amd64`. For Fleur this means an amd64 Bun image on an Apple Silicon daemon fails `smokeContainer`'s `Architecture !== "arm64"` check and, because `smokeImages.arm64` is the arm64 digest, also the `image` identity fact; the readiness policy never reaches an emulated smoke. (What `uname -m` prints inside such a container, and whether the translated process can detect translation from inside the Linux guest, was not found in a primary source; see open question 3.)

**The Fleur process itself under Rosetta.** An x64 Bun binary launched on Apple Silicon is a translated macOS process: Apple documents `sysctl.proc_translated` returning `1` for a translated process and `0` for native, with `ENOENT` meaning not applicable ([About the Rosetta translation environment](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment)). `host.ts` reads exactly this sysctl and cross-checks `hw.cputype` against `process.arch`; under translation `hw.cputype` reports the arm64 machine, `cpuVerified` is false, `translated` becomes `null`, and readiness records a `translated` mismatch. So Rosetta on the host surfaces as the `translated` fact, never as a daemon fact.

### 7. Current caveats of amd64 emulation in Docker's documentation

Docker's current Mac install, FAQ, known-issues and troubleshooting pages no longer carry the earlier statements about Intel images under emulation (crashes under QEMU, `inotify` not working, "best effort"); fetched on 2026-11-09 they contain no such sentences, and the docker/docs source tree returned no match for them. The only current caveat is the Docker VMM statement in section 5. Older statements should not be cited as current.

## Open questions

1. **`seccomp Profile: unconfined` on Docker Desktop.** Two Apple Silicon dumps (Desktop 4.24.0 and 4.36.0) show `Profile: unconfined` while another (Engine 29.1.3) and the CLI reference show `builtin`; a Docker forum poster on 4.36.0 saw `WARNING: daemon is not using the default seccomp profile` on a fresh install. `dockerd --seccomp-profile` defaults to `"builtin"` and `"unconfined"` disables the default profile ([dockerd reference](https://docs.docker.com/reference/cli/dockerd/)), but no primary source found explains which Desktop configurations produce `unconfined`. Fleur's `securityOptions()` only knows `name=seccomp,profile=builtin`, so such a daemon is refused as a daemon identity mismatch. An Apple Silicon qualification should measure this on a fresh default install before choosing a row.
2. **Rosetta default and VMM default.** Docker's docs disagree on the Rosetta default (settings page "Disabled" versus settings reference `true` and release note "enabled by default on macOS 14.1 and later"), and do not state whether Docker VMM or the Apple Virtualization framework is the current default on Apple Silicon (FAQ says Apple Virtualization). Neither is readable from `docker info`; if Fleur wants to record them, it must read Desktop's settings store, which this research did not examine.
3. **In-container view of emulation.** Not located in a primary source: what `uname -m` reports inside a Rosetta-run amd64 container, and whether `docker container inspect` exposes the image platform (the moby swagger read was truncated before `ContainerInspectResponse`). Fleur does not need either, since it refuses on image `Architecture`.
4. **`server.Arch` string on Apple Silicon.** Expected `arm64` from Go's `GOARCH`; not confirmed from a published `docker version` dump.
5. **Bun 1.4.3 x64 asset.** Whether the `x64-baseline` asset the pinned Dockerfile downloads was already an alias of the single x64 binary at 1.4.3, as the current Bun docs describe, was not verified against the 1.4.3 release.
