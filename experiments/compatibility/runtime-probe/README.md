# Pre-application TSYNC feasibility experiment

This is an issue #23 compatibility probe, not Fleur runtime code. A pass establishes only this small Bun/Preact fixture under this filter. It cannot close the runtime isolation gate.

Run on a disposable Ubuntu 24.04 native Linux amd64 or arm64 Docker runner:

```sh
python3 -m unittest discover -s experiments/compatibility/runtime-probe -p 'test_*.py'
python3 experiments/compatibility/runtime-probe/run.py --architecture amd64 > runtime-probe-report.json
# On a native arm64 Linux runner, use --architecture arm64 instead.
```

The driver requires the existing runner's GCC 13.3.0 and refuses other versions. It installs nothing on the host. Evidence records the executed compiler version and binary SHA-256, helper SHA-256, host OS/kernel/Docker versions, immutable base manifest and built image ID. This is an experiment compiler candidate, not a verified release compiler or immutable runner image. Compilation uses `-shared -fPIC -O2 -std=c11 -Wall -Wextra -Werror -pthread`. The build uses the rendering experiment's existing frozen Bun lockfile with Preact 11.0.1 and preact-render-to-string 6.8.0. It asserts Bun 1.4.3 in trusted preparation.

Image preparation may download the pinned official Bun manifest and frozen dependencies. Execution uses the resulting image ID with `--pull=never`. No host mounts, Docker socket, credentials, secret environment, capabilities or network are supplied. Execution has a readonly root, UID/GID 65534, one CPU, 512 MiB memory with swap disabled, 64 PIDs, disabled core dumps, no-new-privileges and a 30-second external timeout. The driver attempts removal of owned containers/images and removes its host build context. The JSON report records each cleanup outcome and fails if removal is incomplete. Resources never attempted are reported as never-created. An unfinished build command may leave Docker daemon work pending; removing the current image tag cannot prove cancellation, so that state also prevents successful completion.

Docker's default syscall filter is explicitly disabled for this experiment. Its presence could disguise missing native enforcement. The helper installs its own deny-by-default filter with `SECCOMP_FILTER_FLAG_TSYNC`, permitting memory, timing, synchronization and signal machinery, exit/close, stdin read and stdout/stderr writes. Unknown syscalls, x32 syscall numbers and alternate filesystem/network/process authority paths receive EPERM. Wrong audit architecture kills the process. Every nonzero installation result blocks application execution, including a positive unsynchronizable thread ID.

The trusted bootstrap imports bundled Preact code and the native helper, reads application source as inert text and warms the renderer. It creates a native witness thread and establishes that `/etc/passwd` is readable before restrictions. Only after successful TSYNC does `new Function` compile/evaluate the application fixture. Its top-level body checks 24 direct syscall attempts for EPERM; renders a literal expected Preact paragraph; and tries Bun's file API. The pre-existing witness thread must also receive EPERM opening the previously readable file. A runtime/filter incompatibility is an experiment failure, never permission to relax the asserted authority restrictions.

Exit zero means the complete, correctly typed bounded report passed and owned resource cleanup completed. Installation must be integer zero; boolean false and malformed JSON values cannot pass. Cleanup failures are reported using resource kinds and outcomes without raw cleanup subprocess output. Nonzero means absent prerequisites, compiler mismatch, build/runtime failure, timeout or failed evidence. Both emit a JSON report with `v1_gate_passed: false`. CI must preserve this report even on failure. The driver is bounded at 240 seconds for image build, 30 seconds for container execution, 30 seconds per metadata/build command and 15 seconds per cleanup action.

## Evidence and limits

Locally executed on macOS: the public report acceptance test failed first because the conservative placeholder rejected complete evidence. After implementing complete-report acceptance, both acceptance tests passed. Python syntax compilation passed. The driver rejected macOS with `bounded_probe_passed: false`. Native behavior required the later Linux runs below.

This does not establish full broker/database-proxy transactions, runtime module/import closure, unrestricted hostile application FFI access, every existing Bun thread's behavior, long-lived async/JIT workload, future thread creation, CPU/memory/PID abuse, client islands or reactive refresh. TSYNC is requested for all existing threads, but this fixture directly witnesses only one pre-existing native thread. New process/thread creation is denied rather than claiming support for restricted future threads. Remaining tests and independent review are required before relying on the architecture. Unsupported platforms remain unresolved.

Independent review fixes: cleanup failure and malformed-report regressions were demonstrated red. After enforcing typed fields and confirmed cleanup, all three report acceptance tests passed. The macOS rejection now reports both resources as never-created with cleanup complete.

## Hardening extension awaiting Linux execution

The extension closes unrelated inherited descriptors during trusted bootstrap. It retains only stdio plus descriptors whose `/proc/self/fd` link identifies kernel eventpoll, eventfd or timerfd bookkeeping. File-backed `mmap`, descriptor duplication and all descriptor transfer syscalls remain denied after TSYNC, and reads/writes remain limited to the identified stdin/stdout/stderr channels. A deliberately opened `/etc/passwd` descriptor must become EBADF before restriction. Any closure or admission error blocks application evaluation. This is not a full runtime module-closure proof.

The application now checks 24 native syscall attempts, including openat2, creat/rename, socketpair, clone/clone3, setns, process_vm_readv, capset, io_uring_enter/register, file-backed mmap, dup and x32 openat. Bun's file API must still fail. These are direct native FFI calls after restriction. Native Preact rendering and a registered request/reply use the same restricted process. The application emits one bounded JSON request on fd1 and receives one bounded reply on fd0. The standalone driver dispatches only the exact `compat.query`/`probe-query`/`readExercise` request and supplies the fixed exercise fixture. This proves the protocol shape when executed, not a PostgreSQL transaction. `protocol.run_container` accepts a trusted dispatch callback for the separate real PostgreSQL broker experiment.

Trusted bootstrap reads the actual cgroup-v2 `cpu.max`, `memory.max` and `pids.max`, requiring one CPU, 512 MiB and 64 PIDs. Separate owned containers run the trusted `abuse` executable without application seccomp. Four busy threads must increase both CPU throttling counters; a surviving parent must observe its pressure child terminated by SIGKILL and positive kernel `memory.events` deltas for both `oom` and `oom_kill`, with `memory.max == 536870912` and `memory.swap.max == 0`; fork pressure must reach `pids.current == pids.max == 64`, fail with EAGAIN and increase `pids.events max`. These demonstrate cgroup enforcement independently of restricted application behavior. The driver externally bounds each abuse container at 15 seconds, then removes every owned resource. The PID fixture kills and reaps its own children before exit. No host mounts, capabilities, network or swap are supplied.

The compiler executable must now match the exact SHA-256 recorded by the previous Linux run, as well as GCC 13.3.0. A runner toolchain update fails closed and needs fresh explicit compatibility evidence. Helper and abuse executable hashes are recorded separately; both derive from that compiler and the immutable Bun image manifest.

Local Python report evidence tests demonstrated red for missing hardening evidence, missing cgroup configuration and a boolean database ID accepted as a valid broker reply. After the fixes, eight Python tests passed, including two actual local pipe exchanges, denial of malformed registered requests/replies and external termination of a stuck local fixture. Python syntax checks passed. On macOS the complete driver rejected unsupported execution before creating resources. Native C compilation, seccomp changes and controlled cgroup abuse have not yet run on Linux. Historical Linux passes above apply only to the earlier ten-control fixture.

Still unresolved: native Intel/Apple Silicon Docker execution and the complete Linux release matrix; runtime import/module closure; direct behavioral witnesses for every existing Bun thread; long-lived async/JIT workloads; end-to-end restricted PostgreSQL transaction/cancellation/outcome evidence; deadline isolation from healthy restricted workers. Future thread/process creation is denied by this experiment rather than claiming support.

## Linux OOM attribution regression

On October 13, 2026, [run 38433432191](https://github.com/hazeion/fleur/actions/runs/38433432191) compiled and executed the hardening extension on Ubuntu 24.04 amd64. CPU pressure recorded 20 throttled periods and 1,987,459 throttled microseconds. PID pressure reached current/max 64, EAGAIN and one limit event. Memory pressure exited 137, but Docker reported `OOMKilled: false`. The report correctly rejected that ambiguous cause and retained `v1_gate_passed: false`; all owned resources were removed. The native worker returned before resource execution, but its evidence was not retained before the later failure, so this run cannot certify its full native controls.

The revised memory experiment forks one pressure child from a small trusted monitor. The monitor samples kernel cgroup OOM counters before allocation and after `waitpid`, records the child's actual terminating signal, and checks the actual 512 MiB/no-swap limits. Successful evidence requires container exit zero, child SIGKILL, and strictly positive `oom` and `oom_kill` deltas. Docker's OOM flag remains reported independently. Exit 137 alone, either Docker flag value, a child failure without OOM counters, or a changed limit cannot pass. This replaces a container-status inference with direct cause evidence under the same approved resource profile.

The public evidence test failed red when supplied complete direct kernel/child attribution, then passed after implementing that requirement. Ten local Python tests now pass with ResourceWarnings treated as errors, including rejection of the original ambiguous 137 shape. Syntax checks and diff whitespace checks passed. The revised native monitor has not yet been compiled/executed on Linux. The attribution failure's exact upstream Docker cause remains unknown; no evidence distinguishes missing event delivery from another SIGKILL in the original run. Native evidence and partial resource results now enter the report immediately so later failures preserve earlier observations.

Independent review found a report-integrity regression in the revised monitor parser: native JSON could supply `container_exit` or `docker_oom_killed` and overwrite driver-measured status. A replay through the real report-producing driver demonstrated red, falsely returning exit zero for a measured exit 137. The parser now requires exactly the five native signal/cgroup fields, rejects nonobjects, conflicting or extra fields, malformed JSON and output over 4096 UTF-8 bytes. Driver-measured status remains separate from admitted native fields. Fourteen local tests pass, including individual status-key collisions, valid evidence paired with actual parent exits zero/137, retained native evidence after malformed memory results, and completed cleanup. These driver tests substitute subprocess results to exercise report interpretation; they do not claim native Linux execution.

## Native AArch64 port awaiting execution

The driver selects only a matching native Linux amd64 or arm64 profile. An explicit `--architecture` requires that architecture on the actual host; it cannot turn an amd64 host plus QEMU into ARM64 evidence. Omitting the option detects one of those supported native profiles. Native Darwin remains rejected. The amd64 and arm64 Bun manifests use the independently hashed architecture pins recorded in the isolation experiment. GCC must report version 13.3.0 and the matching `x86_64-linux-gnu` or `aarch64-linux-gnu` target. Both compiled binaries must have ELF64/little-endian headers with machine 62 or 183, and Docker must report the matching built image architecture. The trusted profile manifest must match the native helper's compiled architecture before restrictions or application evaluation.

The helper selects `AUDIT_ARCH_AARCH64` for native little-endian LP64 AArch64, retains `AUDIT_ARCH_X86_64` for amd64, and refuses unsupported/ILP32/big-endian compilation. Wrong kernel audit ABI still kills the process. The same anonymous-only mmap flags check and fd-limited read/write policy apply to each native 64-bit ABI. The seccomp call still requires exact-zero TSYNC; no new thread/process or shared-library loading syscall is admitted. AArch64 syscall selection follows the [Linux syscall definitions](https://github.com/torvalds/linux/blob/v6.17/include/uapi/asm-generic/unistd.h) and [audit ABI definitions](https://github.com/torvalds/linux/blob/v6.17/include/uapi/linux/audit.h). These source references guide the candidate port; only native execution can verify its runtime compatibility.

Both profiles report 24 ordered native controls. Four controls differ because AArch64 does not expose the same legacy amd64 syscalls or x32 ABI:

| Index | amd64 control | arm64 control |
| --- | --- | --- |
| 1 | `open` | `openat_write` |
| 11 | `creat` | `openat_create` |
| 12 | `rename` | `renameat2` |
| 23 | `x32_openat` | `unknown_syscall` |

The ARM64 unknown-number control requires filter EPERM, rather than accepting kernel ENOSYS as a denial proof. Other controls still cover filesystem mutation, new sockets/connects, process/namespace/debug/privilege changes, io_uring alternatives, file-backed mmap and descriptor duplication. The trusted bootstrap reports native architecture and exact control names; the acceptance boundary rejects mismatched architecture, wrong labels, wrong results and missing evidence. Registered stdio broker exchange, Preact rendering, preexisting-thread witness and actual CPU/memory/PID cgroup pressure remain mandatory on both profiles.

AMD64's existing executed GCC binary SHA-256 remains required. ARM64 currently has no executed compiler digest: `expected_gcc_binary_sha256` is null, `compiler_status` is `candidate-recorded` and `compiler_pin_verified` is false. The driver records its actual GCC executable digest, source digests, compiled helper/abuse digests, ELF identities and immutable image identity. A candidate pass cannot claim a frozen compiler or close the v1 gate. After native CI execution and inspection, freeze the observed ARM64 compiler digest before calling it verified.

Local tests demonstrated red for accepting ARM64 evidence with x32-only labels, rejecting a native ARM64 setup, and accepting the wrong compiled ELF machine despite a matching compiler label. After the port, 22 Python tests pass with ResourceWarnings treated as errors. Syntax checks and whitespace checks passed. Invoking `--architecture arm64` on this macOS host failed closed before creating resources. The ARM64 helper has not yet been compiled or executed natively; independent critical review and native CI are still required. This port does not establish Docker readiness or installation on Intel/Apple Silicon macOS, broader distro support, module closure or long-lived runtime behavior.

For consumers such as the real PostgreSQL broker probe, `report.py` and `runtime_profile.py` have no local-module dependencies and can be loaded explicitly by path. `report.CONTROLS[architecture]` supplies the admitted ordered manifest labels. Prepare `/probe/profile.json` with architecture/control names, copy it into the immutable image, and call `report.accept(evidence, expected_architecture)` to prevent foreign-architecture evidence from satisfying that worker.
