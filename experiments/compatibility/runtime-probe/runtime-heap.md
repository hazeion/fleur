# Runtime heap preparation and verification

The AMD64 VFS worker in [CI 39292274975](https://github.com/hazeion/fleur/actions/runs/39292274975) exited with Docker status 139 before its operation deadline. The pidfd guard reported a premature physical exit, with the parent control channel still open. That establishes an actual worker failure; it does not identify the failing JSC call.

Bun 1.4.3 commit `c6da4a4d3010e5553438c60f6bd76d981976867c` pins WebKit `0c06faadf65bf8e8c8ad3a5a8aca83e1e9ed653f`. Its compiler worklist uses automatic threads that stop after ten idle seconds and can restart when work arrives. Thread creation failure is fatal in that upstream implementation. Therefore warming the engine once does not guarantee that later compilation can reuse an existing thread. [Pinned worklist](https://github.com/oven-sh/WebKit/blob/0c06faadf65bf8e8c8ad3a5a8aca83e1e9ed653f/Source/JavaScriptCore/jit/JITWorklist.cpp), [thread lifetime](https://github.com/oven-sh/WebKit/blob/0c06faadf65bf8e8c8ad3a5a8aca83e1e9ed653f/Source/WTF/wtf/AutomaticThread.h), [thread creation](https://github.com/oven-sh/WebKit/blob/0c06faadf65bf8e8c8ad3a5a8aca83e1e9ed653f/Source/WTF/wtf/Threading.cpp).

The candidate worker configuration uses four supported settings consistently in the runtime and database-worker images:

- `BUN_JSC_useConcurrentJIT=0`: compile on the executing thread while keeping JIT tiers enabled.
- `BUN_JSC_useConcurrentGC=0`: use the stop-the-world marking scheduler while retaining garbage collection.
- `BUN_JSC_numberOfGCMarkers=1`: use one GC marker.
- `BUN_JSC_useWarmUpMarkedBlocks=0`: omit the optional helper that prefaults heap blocks.

Bun itself pairs synchronous compilation with one GC marker for one-shot startup, and applies `BUN_JSC_` options before creating the VM. The block-prefault helper otherwise starts lazily after an allocation threshold. These source-supported settings are a compatibility candidate; native execution must establish whether they fix this failure. [Bun initialization](https://github.com/oven-sh/bun/blob/c6da4a4d3010e5553438c60f6bd76d981976867c/src/jsc/bindings/ZigGlobalObject.cpp), [WebKit options](https://github.com/oven-sh/WebKit/blob/0c06faadf65bf8e8c8ad3a5a8aca83e1e9ed653f/Source/JavaScriptCore/runtime/OptionsList.h).

After TSYNC, the host descriptor audit, and its acknowledgement, every Bun worker runs `verifyRetainedHeap`. Three bounded allocation rounds exercise six forced synchronous collections. Across those collections, 128 retained objects keep their identifiers, strings, and all bytes of their typed arrays. Their 16 KiB of retained buffers and identifier checksum 8128 are checked explicitly. Failure prevents application compilation/evaluation. Success emits the fixed GC verification marker before busy execution and supplies `runtime_gc_verified: true` with detailed counts in the healthy evidence frame. The database worker uses the same bootstrap and probe.

A trusted broker wrapper repeats the proof after every successful registered reply, before returning to application code. This includes the reply following the idle stress pause. It emits a distinct post-broker marker. The native collector is captured during trusted module loading; a later replacement of `Bun.gc` cannot substitute for it. Private verification state is reset before each exchange and set only after the complete probe and marker callback succeed. The final healthy frame requires that latest post-broker proof, so a missing exchange or a caught verification error cannot reuse the initial proof. Each reported set of six collections belongs to the latest probe, not a cumulative collection count.

The original busy application, worker restrictions, resource profile, physical deadline, and late-termination tolerance stay intact. An additional delayed broker acknowledgement can stress compiler-thread idle retirement; it supplements the original concurrent lifecycle checks. Local Bun tests exercise the retained-heap function, while only native CI exercises it under the full worker restrictions. The GC and JIT runtime remain enabled.

The follow-up [CI 39297129581](https://github.com/hazeion/fleur/actions/runs/39297129581) reached startup approval and event controls in the database worker but timed out before the initial heap-complete marker or first broker request. This localizes the missing progress to the initial heap proof, without identifying an allocation or collection call.

The candidate now runs the same trusted retained-heap verification immediately after Preact warmup, before native preparation, descriptor closure, and thread inventory. Its result is discarded. This tests whether initializing heap work before restriction changes the later outcome. It does not establish collector quiescence, prevent later helper restarts, or prove safe thread coordination under the filter. The pinned collector can coordinate existing threads even with one GC marker. Native CI must test this hypothesis. [Pinned collector](https://github.com/oven-sh/WebKit/blob/0c06faadf65bf8e8c8ad3a5a8aca83e1e9ed653f/Source/JavaScriptCore/heap/Collector.cpp).

Both required later proofs retain their allocations, six synchronous collections, and value checks. They emit fixed stage strings at entry, after retained allocation, after each pressure allocation, before and after each numbered collection, and on successful completion. The bootstrap labels these initial or broker stages and limits stage diagnostics to 36 lines and 2048 bytes within the existing 4096-byte stderr ceiling. Repeated broker proofs still execute after the diagnostic budget is exhausted. No application values, paths, addresses, or identifiers enter these markers. The final frame still requires fresh private post-broker evidence; warmup cannot provide it. Local Bun tests establish the fixed stage sequence and unchanged retention evidence, but do not establish native Linux compatibility.

The ARM64 VFS worker in [CI 39300072317](https://github.com/hazeion/fleur/actions/runs/39300072317) passed the primary heap proof and both original busy/healthy lifecycle repetitions. The first added idle repetition completed its eleven-second registered-reply pause, then stopped between `before-collection-0` and `after-collection-0` in the post-broker proof until the unchanged physical deadline killed the worker. Cleanup passed. This establishes a delayed collection failure; the earlier successful collections do not satisfy the idle requirement.

The next candidate adds only the synchronous marking scheduler setting to the existing helper profile. In the pinned `Collector` constructor, `useConcurrentGC=false` selects `SynchronousStopTheWorldMutatorScheduler`; the concurrent scheduler can otherwise resume the mutator while marking continues and reloop. This setting keeps `useGC` enabled and retains the collector thread object. It does not establish that collector-thread retirement, signal coordination, or allocator idle work caused the failure. No restriction, resource limit, deadline, retained value, collection count, or original/additional lifecycle check changes. The full native CI gate must establish whether this scheduling candidate fixes post-idle collection. [Pinned collector](https://github.com/oven-sh/WebKit/blob/0c06faadf65bf8e8c8ad3a5a8aca83e1e9ed653f/Source/JavaScriptCore/heap/Collector.cpp).
