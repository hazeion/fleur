# Arch service startup

This capability is under development. Production installation catalogs remain empty; fixture results do not admit a native release profile.

After confirming the exact installed Arch packages, setup can offer a separate `service-start` action for the authenticated Docker service, Docker socket and containerd service. The plan binds the user, machine, selected system endpoint, exact package profile, unit content hashes, dependencies and current enablement. Installation permission does not authorize startup. Starting these units never authorizes boot enablement, membership changes, socket permission changes or configuration replacement.

Setup verifies actual root-owned unit content and package ownership, loaded fragments and dependency policy. Masked, modified, redirected, changing or unreviewed units return human action. External core dependencies must already be active in this initial scope. An active Docker service is never restarted. Custom and rootless endpoints are preserved rather than converted to system Docker.

Before contacting an Arch system Docker endpoint, doctor passively inventories loaded system socket units and their named Listen/Triggers properties. It compares actual socket type and device/inode, including aliases. A matching activation socket whose service is stopped requires startup authority before any daemon RPC. A complete inventory with no matching activation owner allows an independently managed daemon to be probed normally. Unknown, malformed, inaccessible or truncated observations are not treated as absence. This guard currently covers Arch standard system endpoints; extending it to other installation methods remains separate work.

A matching startup grant is rechecked after fresh observations. Setup durably records a private pending operation and consumes once permission before bounded, noninteractive service control. Unconfirmed termination or startup retains uncertainty and blocks further RPC/retry effects. A confirmed operation still requires actual unit-state and readiness observations; native support remains unverified. Image acquisition and user access remain separately authorized actions.

Tests exercise the public setup/doctor boundary with disposable authority state and external host fixtures. They cover manual-daemon reuse, activation prevention, ownership aliases and drift, grant separation/revocation, unit provenance/dependencies, pending durability, timeout/authentication and unconfirmed completion. They do not establish native systemd/sudo behavior, native permissions, every configuration variant or atomic protection against unrelated host actors changing state between observations. The exact Arch snapshot requires real ordinary-user verification before admission. Service enablement and user enrollment are not implemented by this slice.
