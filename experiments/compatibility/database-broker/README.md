# Disposable database and registered broker probe

This is issue #23 compatibility evidence, not the Fleur runtime. The trusted broker uses internal Drizzle 0.45.4 to construct parameterized PostgreSQL statements and Bun SQL 1.4.3 to execute them. Zod 4.6.7 validates the complete request and public response. The application request contains only a registered operation, bound token, registered action and structural input. SQL, connection URLs, filesystem paths, shell, setup, nested transactions and cross-operation authority are rejected.

Run with a verified Bun 1.4.3 executable and an already available Docker daemon:

```sh
python3 experiments/compatibility/database-broker/run.py --bun /path/to/verified/bun
```

The driver explicitly acquires immutable PostgreSQL 18.6 index `sha256:74935e72241653ca55e0414067e6d8763aceb8a810eb51b452253ec3dcfc4336`. Registry observation on 2026-10-13 resolved Linux amd64 `sha256:885953109528ad3dfc90362b1a6f50a78620b5315be19f187753d267e484dc5b` and arm64 `sha256:a63b24165ea0eacced7585766d790ac08bbaefe10a1841f87783a4505d29a69c`. These are acquired pins, not platform execution results.

No database URL argument exists. The driver creates a random container, ownership label, database and role with an ephemeral random credential. PostgreSQL storage is a container tmpfs, with no host bind mount or persistent data volume. The published port binds exclusively to loopback. Before writes the driver verifies container identity, image digest, PostgreSQL 18.6, database and role. Before removal it verifies ownership again. Cleanup failure fails the report. No development data is used.

The driver runs real SQL tests twice and then connects the restricted native worker to the actual owned database through the trusted broker. Native execution currently requires the same Linux amd64 and GCC pin as the runtime probe. They cover registered reads, invalid-output and child-constraint rollback, two expected-version writers with one winner, cancellation and verified rollback before connection reuse, queued reservation cancellation, isolation of healthy work, actual request-worker termination before commit, committed response loss without replay, and Read Committed statement snapshots with PostgreSQL read-only enforcement. Database tests observe stored state deliberately because committed versus rolled-back data is the contract being proved. A controlled loopback PostgreSQL wire proxy observes the upstream COMMIT CommandComplete frame, then drops or withholds its acknowledgement. Separate reads prove exactly one persisted write while the broker returns outcome-unknown. The proxy also withholds rollback and idle-verification replies to prove bounded cleanup and disposal. Its target can only be the owned loopback database. Frames are bounded at 1 MiB and sockets expire after six seconds. Compiler, oxlint, full ESLint and Bun bundle checks also run. `skipLibCheck` remains false. A required strict compiler failure leaves the driver failed even when runtime tests pass.

The native worker IPC seam is `ipc.ts`. A trusted host launches `bun ipc.ts` with only the owned database environment created by `run.py`. It accepts JSON lines on stdin and returns `broker-response` JSON lines. An admitted fixture request is:

```json
{"kind":"broker-request","operation":"compat.query","token":"probe-query","action":"readExercise","input":{"id":1}}
```

Only a successful validated response for id 1 and name `Squat` authorizes the runtime probe's `registered:Squat` acknowledgement. The trusted host fixes the IPC process to a query Session. A perfectly valid known mutation request is still denied on that channel. Fixed tokens are fixture registration markers, not a production authentication design. The `native.py` helper compiles the separate runtime probe's exact bootstrap and restriction helper, then exchanges the worker's actual request through `protocol.run_container`. The worker receives no database environment and has no network or host mounts. `rpc.py` bounds trusted host RPC at eight seconds independently of the worker watchdog, while the broker bounds each database operation at five seconds. Its silent-process regression proves that expiry terminates the trusted process. The separate runtime probe owns the restriction implementation. This broker does not expose the SQL connection or the trusted code to an application worker.

## Executed local evidence and limits

The request-denial test first failed because the initial admission stub accepted an undeclared `sql` field. Strict schema implementation then passed 13 assertions across the first two admission tests. A subsequent session-confusion regression failed before the trusted-session binding was added, then passed 14 assertions across three admission tests. The bundle built with Bun 1.4.3 and oxlint passed. Strict TypeScript 7.0.2 initially reproduced upstream Drizzle declarations errors. The independently diagnosed declaration repair now passes strict compilation, with exact gel 2.2.1 and mysql2 3.24.6 optional declaration peers. The checked-in `patches/provenance.json` and `patch.test.ts` verify repaired declarations against source maps and unchanged upstream runtime hashes. No runtime code or application dependency permission changed. Full ESLint also passes with its independently pinned TypeScript 6.0.3 engine. This macOS host has no Docker daemon, so database tests have not been executed here. The driver reports this as failure with no completed database checks. Hosted execution must supply real database evidence, not convert the missing prerequisite into a skip or success. An intended SQL red failure cannot be recorded without that prerequisite; SQL assertions are unverified until hosted execution.

The probe does not yet prove joined reads under a controlled concurrent commit, host response loss from process termination, admission queue limits or a full OS matrix. Transport fault tests and native database exchange are implemented but have not executed on this host. Six Python ownership/RPC tests pass, including daemon creation followed by client timeout/error and refusal to remove another owner's container. SQL regression red evidence remains pending hosted execution. No dependent product implementation is authorized by partial results.

The cancellation probe uses one awaited trusted PostgreSQL control path. It verifies the borrowed backend PID and start time, sends cancellation only to that same database/user/backend, waits for the original statement to settle, then verifies rollback and idle work before reuse. If verification stalls, `pg_terminate_backend(pid,200)` waits for actual termination. Confirmed disappearance also permits release; unavailable control authority quarantines the reservation. The positive-timeout termination guarantee follows the [PostgreSQL 18 server signaling contract](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADMIN-SIGNAL). `ReservedSQL.close` is intentionally excluded from disposal because the exact Bun runtime closes its shared pool.

Real hosted execution isolated a Bun test boundary bug in the read-only negative fixture. A lazy SQL Query must first be assimilated to a native Promise before `expect(...).rejects` can start it. The test still executes the forbidden PostgreSQL UPDATE and requires SQLSTATE `25006`, carried by Bun's `errno` alongside wrapper code `ERR_POSTGRES_SERVER_ERROR`. An owned protocol-error listener reproduced the stalled matcher twice and verified the corrected matcher twice; it does not replace real PostgreSQL read-only evidence.

Before database dispatch, the trusted native observer verifies the owned container label and image, then reads every existing worker thread's admitted status fields while the worker blocks on its broker channel. The host independently requires no-new-privileges and the sole native seccomp filter on every observed TID. Worker JSON cannot supply or replace `host_threads`; the driver injects only its captured measurement before acceptance. This inspection uses the runtime probe's fixed read operation with a five-second bound.

The cleanup lease expires before its timeout rejects and before its connection is released or retired. Every awaited cancellation, original statement, rollback and idle verification checks that lease before proceeding. Controlled settlement regressions first demonstrated late SQL on expired authority, then verified no further SQL after delayed statement, rollback or cancellation settlement. These lifecycle tests do not substitute for the real PostgreSQL fault suite.

The last real PostgreSQL fault test isolated a Bun 1.4.3 private-client shutdown stall after a withheld cancellation acknowledgement. Control clients now run only in a short-lived trusted Bun helper. Its strict request selects fixed cancel/terminate SQL for the captured backend and owned target. Database credentials exist only in the helper's trusted environment; stdout contains only the result enum. A 250 ms reply budget ends in SIGKILL and confirmed process exit, with a separate 500 ms exit/stream-cleanup bound. No control result is returned before process death; an unverified exit is unsafe. The helper also has its own exit timer for host disappearance. This avoids closing the healthy shared actor pool or abandoning an unfinished SDK client.

The owned reply-then-stall lifecycle regression first failed after 400 ms with the child still alive, then passed after the shutdown fix. Its budget was aligned to the required 250 ms before the matching old-lifecycle negative control was rerun and failed again. A preliminary 100 ms cold-start failure was a fixture budget mismatch, not evidence of the shutdown regression. Both the replied and silent child cases now verify SIGKILL termination. The unchanged five-second real SQL retirement test still requires a new backend tuple and healthy subsequent queries/mutations.

Lifetime fixtures establish their premises explicitly. The replied-child test waits for its own READY handshake before starting the 250 ms RPC/lifetime boundary; the production launcher still counts startup and RPC together in that same budget. A ready-child old-lifecycle negative control still failed with lifetime-exceeded before the fixed implementation passed. The Python reply fixture likewise confirms readiness before its unchanged 200 ms RPC deadline. The partial-output timeout fixture uses Unix printf and exec sleep to avoid unrelated interpreter initialization while retaining its deadline and redaction assertions. These fixture changes do not raise the real SQL test deadlines.
